# Native continuous playback

On authenticated browsers with native HLS support, MusicBit uses one HLS source for a listening queue. Song boundaries are HLS discontinuities inside the same source: native playback continues without JavaScript assigning another URL or calling Play at each boundary. The production player keeps one HTMLAudioElement for its entire lifetime and uses no WebAudio, Blob URLs, extra audio elements or silent keepalive tracks.

The server checks cached sources with FFprobe. AAC-LC at 44.1 kHz with two channels is copied into two-second MPEG-TS segments; other codecs, AAC profiles, sample rates and channel layouts are converted to that canonical format. If the probe cannot establish compatibility, conversion is used instead of assuming that stream copy is safe. The manifest counts complete AAC frames, including the final frame whose MP4 duration can be trimmed, so cumulative song boundaries match the MPEG-TS decoder's actual presentation timeline.

FFmpeg is included in the API Docker image and required on native API installations. Authentication responses include availability so the app configures native HLS before its first interactive paint. Older servers fall back to `GET /api/me/continuous`. Set `MUSICBIT_CONTINUOUS_ENABLED=false` to disable it. Unsupported browsers and guest sessions keep progressive playback.

Session creation still calls `audio.play()` synchronously in the user's gesture, before submitting its queue. The first native manifest request briefly waits for that authenticated plan. A failed initial plan is retried with a bounded delay; replacing or cancelling the session aborts its requests and retry timer. The server prepares the current song and two ahead, then advances preparation from native segment requests.

With **Ascolto infinito** enabled, the server selects new songs from the current listening seed and the account's history, favorites and taste preferences. It excludes a bounded recent history and the upcoming queue. Empty recommendation batches and transient catalog failures are retried with backoff without closing the native playlist. Each new listening step updates the seed; the page is not responsible for requesting another radio batch while suspended. Browsers without native HLS use the progressive radio connector with the same account context, ahead-of-time recommendations and bounded retry delays.

The app maps the HLS presentation timeline back to each song's position and duration. Skip and seek reuse the source when the target is prepared. Infinite sessions retain twenty tracks behind the native request cursor and the current preparation window, rather than ending after 500 generated songs. `queueStart` identifies the first retained absolute program index. Track indices and cumulative start times remain absolute while `MEDIA-SEQUENCE` and `DISCONTINUITY-SEQUENCE` advance; the app compacts its displayed queue without replacing the native source or resetting its clock. Monotonic snapshot revisions prevent delayed metadata responses from restoring older tracks or autoplay settings. If a pause or backward selection leaves the audible clock before the new window, the client retains that track's identity until the clock catches up; selecting an expired track starts a fresh source.

Queue reordering starts a replacement session in the queue-edit command, preserving the current position and paused state. A finite playlist with `EXT-X-ENDLIST` cannot be reopened by appending bytes: enabling infinite listening or extending a completed queue creates a replacement session that preserves the current position. Explicit Play is required after a page reload. Repeat controls still depend on page execution and have no physical locked-screen validation in this delivery mode.

There are at most four sessions total and two per account, one concurrent conversion process, a thirty-second conversion deadline, and a 512 MiB shared temporary working budget. This temporary segment working area is separate from the persistent 5 GB-per-account source cache. Removed segment identities remain available for the longest published playlist window plus a segment duration, so a client holding an older manifest can finish its requests. Under working-storage pressure their bytes can be regenerated from cached audio during that grace period. Preparation leases protect requested files from concurrent eviction; HTTP opens a file descriptor before releasing that protection. Inactive sessions expire after twenty minutes; shutdown removes working files. Session URLs require the owning account cookie and never reveal signed upstream URLs.

Explicit song selections restart the selected track, including A → B → A and cached progressive sources. Only pause/Play or explicit restoration of a saved listening session retains the position. Source selection installs a single native seek transaction after metadata is available. Native `seeked`, `playing` or plausible advancing clock progress acknowledges that transaction independently of the server metadata request. One correction can reject an old cached native position at initial startup; later `canplay` and `playing` events never replay an acknowledged seek. This prevents a short rebuffer from rewinding a song when its timeline response is delayed.

A settled native `seeked` event also completes a manual selection within an already-playing HLS source, which need not emit another `playing` event. Changing the upcoming queue preserves the current track position.

Diagnostics show `native-continuous-hls-v8`, the selected transport and source URL. Automated tests use real local AAC/TS over HTTP, measure decoded PCM through the native element, suspend page JavaScript across a song boundary and advance a sliding HLS window while checking the absolute clock and queue compaction. Native HLS tests run only where the browser exposes that decoder; Windows WebKit skips them and still runs the progressive playback suite. These are distinct from physical iPhone lock-screen and CarPlay behavior. See the [test record](ios-test-report.md).
